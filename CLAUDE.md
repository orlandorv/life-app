# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Life — a mobile-first, offline-capable personal app, installable as a home-screen PWA on iOS via GitHub Pages. Life is the shell (home screen + routing); each area of life is a **section** inside it. Built sections: **Gym** (exercise library, templates, live workout logging, rest timer, history, personal records, XP/levels/badges), **Nutrition** (a MyFitnessPal-style diary: meals, calories remaining, carbs/protein/fat, Open Food Facts search, barcode scanning, portions), **Habits** (recurring habits on every day or chosen weekdays, with streaks, a Today checklist and a Week grid, and backfilling past days), **Body** (daily weight, sleep and steps, with a smoothed weight-trend chart, weekly averages and editable history), **Videos** (a watch-list of helpful videos, grouped into free-text topics rather than a fixed list) **Tasks** (a due-date to-do list, bucketed by how soon each is due, that can hand a task to the real Calendar app as a `.ics` file) **Journal** (a daily mood and energy check-in with a note, and the patterns it makes with your training and sleep) and **Inbox** (quick notes and ideas, sorted by #tags written into them, that can become a task). All eight home-screen cards are live.

### Layout

- `index.html` — the Life shell: `#life-home` (section grid) and `#gym-section` (all Gym markup: tabs, rest bar, bottom nav). Gym's modals sit after it, at body level.
- `life/life.js` + `life/life.css` — router, home grid, service-worker registration, and the modal chrome shared by every section (close buttons, backdrop tap, Escape, delegated from `document`); `life.css` also holds the shared foundation (reset, `:root` design tokens, body rules).
- `life/dom.js`, `life/stepper.js` — shared UI primitives used by every section (element builder, modal stack, toast, `confirmSheet`, −/+ stepper). Import these, don't copy them.
- `life/db.js` + `life/dates.js` — **LifeDB** (see below) and local-day helpers (`localDayId`, `addDays`, `dayLabel`). Use local days, never `toISOString().slice(0,10)`, which is UTC.
- `life/backup.js` + `life/backup-format.js` — Life-wide backup and restore (see Backup below). `backup-format.js` is pure and unit-testable in Node.
- `life/share.js` — `shareOrDownload(file, title)`: hands a generated file to the Web Share API, falling back to a plain download. Shared by Backup and Tasks' calendar export — both need the same "must start straight from the tap on iOS" handling.
- `life/storage-errors.js` — pure: `isStorageError()` (is this thrown value a failed IndexedDB/quota write?) and `mayWarnAboutSave`, a 30-second gate shared by every "couldn't save" toast. Unit-tested.
- `life/review.js` — the Sunday weekly review: pure, builds the week's numbers from what the sections already keep and words them as one row per section (see Today). Unit-tested.
- `life/svg.js` — `svg()`, the one createElementNS helper behind every hand-built chart (Body's, the lift history's, the Nutrition week's). Import it; don't write another.
- `life/updates.js` — registers the service worker, looks for a new version when the app returns to the foreground, and shows the "A new version is ready · Reload" banner (see PWA / offline layer).
- `life/daybar.js` — the shared ‹ label › day/week switcher (`dayBar()`); its styles, plus `.life-main`, live in `life.css`.
- `body/` — the Body section: `body.js` (screen + entry sheet), `store.js`, `stats.js` (pure trend/weekly-average/chart-geometry/reminder maths, unit-testable in Node), `chart.js` (hand-built SVG: the weight line chart and the daily bar chart), `health-import.js` (pure: parse Apple Health text, plan the save) + `health-sheet.js` (Paste from Health UI and setup guide), `body.css`.
- `habits/` — the Habits section: `habits.js` (Today/Week views + habit sheet), `store.js`, `streaks.js`, `routine.js` and `times.js` (pure schedule/streak, routine-step and time-of-day maths, unit-testable in Node), `routine-sheet.js` (a routine's checklist, also opened from Today), `step-editor.js`, `habits.css`.
- `nutrition/` — the Nutrition section: `nutrition.js` (diary, week view + add-food sheet), `store.js` (state and writes), `portions.js`, `totals.js` and `week.js` (pure food/portion/meal, total and week maths, unit-testable in Node), `whole-foods.js` (the built-in whole-food list and its search), `colombian-foods.js` (its Colombian rows, from ICBF's table) and `stores.js` (the UK supermarkets), all pure, `off.js` (Open Food Facts client), `scanner.js` (camera barcode scanning), `nutrition.css`.
- `vendor/zxing/` — ZXing barcode decoder (`@zxing/library` 0.23.0 UMD, Apache-2.0, LICENSE alongside). Vendored because there's no build step; loaded lazily by `nutrition/scanner.js` on first scan and deliberately **not** in `APP_SHELL`.
- `videos/` — the Videos section: `videos.js` (grouped list + add/edit/rename sheets), `store.js`, `organize.js` (pure grouping and YouTube-link parsing, unit-testable in Node), `oembed.js` (best-effort title lookup), `videos.css`.
- `tasks/` — the Tasks section: `tasks.js` (bucketed list + add/edit sheet), `store.js`, `organize.js` (pure due-date bucketing, unit-testable in Node), `recurrence.js` (pure: repeating-task dates and the calendar's repeat rule), `ics.js` (pure `.ics` file building, also unit-testable), `tasks.css`.
- `journal/` — the Journal section: `journal.js` (day bar, check-in card, patterns, recent list), `store.js`, `insights.js` (pure: the 1–5 scales, the check-in streak and the mood/energy patterns, unit-testable in Node), `journal.css`.
- `inbox/` — the Inbox section: `inbox.js` (capture box, search, tag chips, note list + note sheet), `store.js`, `organize.js` (pure: #tag parsing, search, ordering and note-to-task, unit-testable in Node), `inbox.css`.
- `tests/` — zero-dependency Node tests for the pure modules and the silent-failure checks (see Commands). Not part of the app and not in `APP_SHELL`.
- `gym/js/*.js` + `gym/gym.css` — the Gym section. Its entry point is `bootGym()` in `gym/js/app.js`.

**Routing** is a hash: `#/` is Today (home), `#/<section>` a section, `#/<section>/<action>` a section opened straight into something (see Today below). `route()` shows the one `#<id>-section` matching the hash, sets `body[data-section]`, and calls that section's optional `enter(action)`. Gym is booted once at startup and only hidden/shown, so an active workout, stopwatch and rest timer keep running while you're on the home screen. Gym's selectors are scoped to `#gym-section` — keep new Gym code from using bare global selectors.

**Adding a section:** add an entry to `SECTIONS` in `life/life.js` (with an `enter` function if it needs to load data), add its container (`<div id="x-section" hidden>`) and any modals as static markup to `index.html`, add its stylesheet `<link>`, and add its files to `APP_SHELL` in `sw.js`. Store its data in LifeDB by adding stores and bumping `DB_VERSION` in `life/db.js`. Life-owned classes are `life-` prefixed; Gym's generic classes (`.btn`, `.modal`, tokens) are reusable as the shared design system.

Vanilla JS throughout: no framework, no bundler, no npm dependencies, no build step. `life/life.js` and `gym/js/*.js` are loaded as native ES modules straight from `index.html` (`<script type="module" src="life/life.js">`). Edit a file, refresh the browser.

## Commands

Run the dev server (a zero-dependency static file server, `server.js`):

```bash
node server.js
```

Serves on `http://localhost:8000`. (Also runnable via the `.claude/launch.json` "Gym Tracker" preview config (name kept; it serves all of Life).)

Regenerate the smaller PWA icons from the master `icons/icon-512.png` (uses macOS's built-in `sips`, no dependencies):

```bash
tools/make-icons.sh
```

Writes `icons/icon-{180,192}.png`. To change the artwork, replace `icons/icon-512.png` (square, full-bleed — iOS rounds the corners itself) and re-run this.

Run the tests (zero dependencies: Node's built-in `node:test`, Node 22+):

```bash
node --test "tests/*.test.mjs"
```

There is no linter or build step. The tests cover the **pure** modules and the things that go wrong silently: `app-shell.test.mjs` (every file the app loads is in `sw.js`'s `APP_SHELL` and exists; every import between shell modules resolves to a listed file — **run it before every commit that adds a file**), `backup-format.test.mjs` (a round trip through the restore validator with a sample row per store, and that every store rejects a damaged row — add a sample row when you add a store), `dates.test.mjs` (month/year/leap/clock-change edges; also run it with `TZ=Pacific/Auckland` and `TZ=America/Los_Angeles`) `gym-data.test.mjs` (every stock exercise has substitutes, a demo and a strength-standards entry, and sane sets/reps/RIR/rest in every rep scheme), `progression.test.mjs` (the XP-safety fuzz and every progression rule below), `plate-math.test.mjs`, `warmup.test.mjs`, `review.test.mjs`, `lift-history.test.mjs`, `habits-streaks.test.mjs`, `recurrence.test.mjs`, `nutrition-week.test.mjs`, `checkin-derive.test.mjs`, `next-plan.test.mjs`, `plan-from-workout.test.mjs`, `saved-meals.test.mjs` and `service-worker.test.mjs` (runs the real `sw.js` against a fake worker with an in-memory Cache Storage and a scriptable network). Anything that touches the DOM or IndexedDB isn't covered; verify those in the preview (see the gotchas under Reordering). `tests/package.json` only marks that folder as ES modules — don't add `"type": "module"` at the repo root, where `server.js` is CommonJS.

## Deployment

Static hosting on GitHub Pages; see `DEPLOY.md` for the full walkthrough. The important constraint for any code change: **every asset reference must stay relative** (`life/life.js`, not `/life/life.js`) because Pages serves the site from a repo subpath (`/repo-name/`), not the domain root. This applies to script/link tags in `index.html`, paths inside `sw.js`, and the manifest's icon paths.

## Architecture

### Design system (`life/life.css`, `life/icons.js`)

Warm and calm: paper background, white cards, ink text, one colour per section. **Change colours as tokens in `life/life.css`, never in a section's CSS.**

- **Tokens:** surfaces `--bg` (paper) / `--bg-raised` (cards) / `--bg-secondary` (wells, tracks); `--text-primary` / `--text-secondary`; section colours `--gym`, `--nutrition`, `--habits`, `--body`, `--videos`, `--tasks`, `--journal`, `--inbox`; `--card-border` / `--card-shadow` for anything card-like; `--radius` / `--radius-sm`. Dark mode redefines them all under `prefers-color-scheme: dark`.
- **`--primary` follows the section.** `route()` sets `body[data-section]`, which maps `--primary` to that section's colour, so buttons, links, steppers, progress and modals (which sit outside the section container) all take it. On Today it's `--ink`.
- **Text on a coloured fill uses `--on-accent`,** not `#fff`: white in light mode, dark ink in dark mode where the fills are lighter. Every section colour keeps ≥4.5:1 on the page and on cards in both modes. On a well (`--bg-secondary`) Gym, Nutrition and Body fall just short as *text* in light mode (4.42, 4.29, 4.47); they were left alone because they are the brand colours and text in that spot is rare. `--text-secondary`, `--warning` and `--success` were darkened in light mode so they clear 4.5:1 on all three surfaces (re-check with a contrast script, not by eye, if you touch them); dark mode already did.
- **Type:** `--font-sans` for UI; `--font-display` (New York serif on Apple devices) for page and sheet titles and the greeting; `--font-rounded` for big figures. System fonts only, so it works fully offline.
- **Icons:** `life/icons.js` — 24px line icons, one stroke weight, `currentColor`. Build with `icon(name)`; in static HTML use `<span data-icon="name">`, swapped in by `hydrateIcons()` at start. No emoji in UI chrome.
- **Shared pieces:** `.life-surface` (card), `.life-list` (grouped list with hairlines — rows inside drop their own box), `.life-empty` (icon + title + line), `.life-eyebrow`, `.life-daybar`, `.life-check` (a checkbox with a label, in a row). Gym's `.btn`, `.card`, `.modal*`, `.stepper*`, `.segmented`, `.form-input` in `gym/gym.css` are the shared form controls. A style used by more than one section belongs here, not copied into each — `.life-check` moved here from Nutrition once Videos needed it too.
- **Tap targets are 44px where there's room.** A control drawn smaller (`.icon-btn`, `.segmented button`, so the sheets' 32px ✕) keeps its look and borrows the space around it through an invisible 44×44 `::after` (`life.css`), which paints and moves nothing. That only works with free space around the control: a pseudo-element paints over its *neighbours*, so crowded rows get real size instead — the plan editor's step tools get no borrowing, and the set rows below are sized for real. Plain text links (`.link-btn`) are ~25–30px tall, which meets WCAG 2.2's 24px minimum but not 44; Inbox's tag chips are 34px. The Tasks tick box was already 44.
- **The set row's columns are one custom property** (`--set-columns` in `gym.css`, used by the rows *and* their header, so they can't drift): `20px 1.3fr 1fr 56px 44px`. Weight gets the spare width because it is the number that needs it — a weight like `142.5` must be readable, and at 375px it used to be cut to "14" — at the cost of narrower −/+ buttons (28px wide, 22px for RIR), which are 44px *tall*. Checked to fit at 375, 393 and 430px; at 360px weights of 100+ still clip a little.
- **Focus and zoom:** one `:focus-visible` ring in `life.css`, in the section colour (taps never show it; keyboard, switch and screen-reader focus does). Text fields and sheets set `outline: none` more specifically because they have their own focus look (border + glow; the stepper lights its whole border via `:focus-within`), and a stepper's own buttons ring *inside* because the stepper clips its children. `html` has `touch-action: manipulation` (no double-tap-zoom delay; pinch is untouched). **The viewport keeps `maximum-scale=1.0` on purpose:** iOS has let people pinch-zoom regardless of it since iOS 10, and it is what stops Safari zooming the page when a field under 16px is focused — the set rows' stepper numbers are 13–14px (and the weight slot is only ~24px wide), so removing it would zoom on every weight/reps tap. Take it out only together with giving those inputs 16px.

### Nutrition data (`nutrition/portions.js`, `off.js`, `scanner.js`)

- **Foods** hold nutrition `per100` (per 100 g/ml) and/or per `serving` (`{grams?, kcal, proteinG, carbsG, fatG}`), plus `baseUnit` 'g'|'ml'. Foods saved before portions existed have bare `kcal`/`proteinG` (one serving); `normalizeFood()` reads every shape — always go through it rather than reading fields directly.
- **Entries are snapshots** (`amount`, `unit` 'serving'|'g'|'quick', `meal`, and the computed nutrients), so editing or deleting a food never rewrites history. Old entries without `meal` are filed by `loggedAt` time (`mealOf()`); without `unit` they edit as quick entries.
- **Whole foods are built in** (`whole-foods.js`): ~125 everyday foods, plus the Colombian foods below (eggs, bananas, chicken, rice, oats…) that work offline, each with a natural portion — `servingLabel: ['medium egg', 'medium eggs']`, so a banana logs as "1 banana (118 g)" and `portionLabel()`/`servingName()` use that wording. They're typical averages per 100 g/ml from standard composition tables, **not any shop's**; raw and cooked are separate foods and the name says which. Like an Open Food Facts product, one is saved to `foods` (id `whole-<slug>`) the first time it's logged. When adding rows, check each one's calories against 4·protein + 4·carbs + 9·fat (within ~20%; fibre explains the gap on veg) — that's what catches a typo in a hand-entered table. To add a food, add a row to `DATA`; give it a unit (`'ml'`) if it's a liquid outside Drinks, and aliases for what people call it (aliases only match words of 4+ letters, so "egg" doesn't find the aubergine).
- **Colombian foods** (`colombian-foods.js`, categories `Colombian dishes` and `Colombian staples`): 74 foods copied from ICBF's *Tabla de Composición de Alimentos Colombianos*, 2018 edition (icbf.gov.co/system/files/tcac_web.pdf), the country's official composition table. Each row's `reference` names its line in the table (`Source: ICBF TCAC 2018 (S025)`) and shows on its portion screen; don't retype numbers from memory, take them from the table. Conventions to keep in mind: values are per 100 g edible portion; **kcal is ICBF's own** (4·protein + 9·fat + 4·*total* carbohydrate + 2·fibre, FAO 2003) so it can sit above 4P+4C+9F where there's fibre, and it reads higher than UK-label convention for vegetables; **carbs are total carbohydrate** (fibre included). The table gives **no served-portion weight** for anything, so `serving` is null and these are logged in grams. The table is a scanned PDF with no text layer — it was read with OCR and every row checked against ICBF's own energy formulas in both kcal and kJ and against a sum-to-100 g balance, with the few the OCR stumbled on confirmed against the printed page. **Cuy asado is the one row not from the 2018 table**: its water is 49.9 g there against 61.1 g in ICBF's earlier booklet (*Caracterización y composición nutricional de 18 preparaciones tradicionales*, 2017, ISBN 978-958-623-189-3), with identical protein, fat and ash, which makes carbohydrate-by-difference 14.8 g for a roast meat — a typo in the table, so the booklet's laboratory figures are used and say so. For the other 17 dishes both publications agree on protein and fat; Mazamorra chiquita differs by 2 g of water (6.1 vs 8.1 g carbs), and the 2018 value is used.
- **Shops** (`stores.js`): Tesco, Aldi, Lidl, Sainsbury's, Asda, Morrisons, M&S, Waitrose, Co-op, Iceland. A shop chip in the add sheet narrows the *online* search to that shop's real products (Open Food Facts' `stores` tag filter), tags each result with it, and filters your own foods; whole foods step aside while one is chosen. A food carries an optional `store` (from Open Food Facts via `storeFromOff()`, or typed on a food you create) that's shown beside the brand and logged with the entry. Open Food Facts' own `stores` field is a free-text list of every shop a contributor named, often foreign ones, so only a recognised UK shop is ever shown. Supermarket own-brand products are deliberately **not** typed into the app: their calories come from the live label data, not memory.
- **Open Food Facts** (`off.js`): search uses `uk.openfoodfacts.org/cgi/search.pl` (UK-sold products first, sorted by popularity); barcode lookups use `world.openfoodfacts.org/api/v2/product/`. No key; only the search text or barcode is sent. **It turns away roughly half of requests under load** with a 503 page that has no CORS headers, so a browser reports it as a bare `TypeError`, indistinguishable from a dropped connection — `getJson()` therefore retries those (and real 5xx) up to five tries with a growing back-off, and `searchFoods()` keeps answers in memory for the session (the sheet also offers **Try again**). Offline, a timeout, and a superseded search are not retried. Foods are saved locally the first time they're logged (id `off-<barcode>`), so they work offline after that. `fromOpenFoodFacts()` skips products without a name or calories and converts kJ-only energy.
- **Saved meals** (`nutrition/saved-meals.js`, LifeDB `savedMeals`): **Save as meal** on any meal in the diary that has food in it names the combination (e.g. "Usual breakfast"); **My meals** then tops the add-food sheet, and one tap logs every food of it into the meal chosen in that sheet's picker (Breakfast/Lunch/…), on the day being viewed. Pure and Node-tested.
  - **A meal's items are diary-entry snapshots** (`snapshotOf()`: the entry minus its id, day, meal and logged time), the same way an entry is a snapshot of a food: the calories and macros are as they were when saved, editing or deleting the food later never changes a meal, and logging one needs no food lookup, so it works offline and for foods since removed. Logging writes fresh entries with new ids, stamped a millisecond apart so the diary (which lists a meal by time logged) keeps the saved order.
  - **Saving under a name you already have replaces that meal** (case-insensitive; same id and creation date, new foods and the name as you typed it), which is how you keep "Usual breakfast" up to date; the sheet says so as you type. Most recently used first. Deleting a meal asks first and leaves food already logged from it alone.
  - **Backup:** `savedMeals` is in `LIFE_STORES` with a row check (`isValidSavedMeal()`: a name, at least one named food, a creation time) and counted in the import preview ("2 saved meals"); a damaged one refuses the whole file before anything is written. Additive: `LIFE_VERSION` unchanged, older backups restore as before.
- **Week view** (`nutrition/week.js`, the **Day | Week** switch at the top of the screen): the week (Monday to Sunday) around the day you were on, with ‹ › to step through weeks and a **Daily average** card — calories (against the target, "kcal of 2,300"), carbs/protein/fat with the same progress bars as the diary, and "Protein target reached on 3 of 5 logged days" — a seven-bar calorie chart with the target as a dashed line, and a row per day that opens that day's diary (a day with nothing logged says so, and still opens). `weekSummary()` is pure and tested in Node; the Sunday review's nutrition line is built from it too, so the two can't disagree.
  - **A day you didn't log is a gap, never a zero:** averages are over the logged days ("Averaged over the 3 days you logged, out of 4 so far"), a gap has no bar, and a target of 0 or blank is no target. Today is included as it stands, and the card says so.
  - **Reading the week never moves the diary:** `loadDays()` returns the entries without touching `state.day`/`state.entries`, so switching tabs or stepping weeks doesn't change which day the Day tab shows. Opening the screen always starts on Day, today. `renderNutrition()` draws whichever view is current, so saving Targets from the Week tab stays on it.
  - The chart's scale tops out on a round number above the biggest day *and* the target (`chartTop()`), bars start at the baseline so height is the value, and each value label has a halo in the card's colour so the dashed line can't cut through a number.
- **Scanning** decodes cropped camera frames with ZXing, restricted to EAN-13/8 and UPC-A/E. Barcodes are compared as 13 digits (`foodByBarcode`) because an EAN-13 starting with 0 is reported as a 12-digit UPC. Typing the number in the scan sheet is the fallback when the camera is blocked or missing.
- **The service worker only caches same-origin requests.** Open Food Facts calls pass straight through, so results are never stale and the cache can't grow unbounded — keep that guard if you touch the fetch handler.

### Body charts (`body/stats.js`, `chart.js`)

Three cards, three shapes, because the data is three kinds of thing. **Weight** is a noisy reading, so it's dots with a smoothed trend line (`chartLayout()`). **Steps and sleep** are whole-day totals, so they're **bars** with a 7-day rolling average line (`barChartLayout()`, `rollingAverage()`), one `TREND_CHARTS` entry each in `body.js`. All three share `state.range` (30/90 days), so changing it on any card changes them all.

- **A day you didn't log is a gap, never a zero** — in the bars, and in the average, which only counts logged days. The average line only appears where a day's 7-day window has at least 3 logged days (`minDays`), so one reading can't pose as a trend; below that the legend says why there's no line.
- Bars always start at 0 (a bar's length *is* its value) and the top rounds up to a readable number (`niceCeil()`: multiples of 4,000 steps, min 8,000; 4 h, min 12 h). Needs two logged days to draw, same as the weight chart.
- Sleep also shades a 7–9 h band (a common adult target — a reference, not a goal the app sets); steps have none. The top is always at least 12 h so the band is always on the chart.
- Today's step bar is usually incomplete until midnight, and the legend says so when today is shown. Today is still counted in the average, as it is in Weekly averages.

### Apple Health import (`body/health-import.js`, `health-sheet.js`)

A home-screen web app can't read HealthKit, so a user-built Apple Shortcut ("Life: copy Health") copies the last few days as text — `steps YYYY-MM-DD <count>` (grouped by day), `weight YYYY-MM-DD <value> <unit>` (every weigh-in, oldest first) and `sleep YYYY-MM-DD HH:mm <duration> <stage>` (one line per Sleep Analysis segment) — and **Paste from Health** in Body reads it with `navigator.clipboard.readText()` (must be called straight from the tap), previews, and saves on confirm. No key, account or server; nothing leaves the phone. The setup steps live in the app (`showHealthSetup()`) since the Shortcut is built on the phone.

- `parseHealthText()` is deliberately forgiving (thousands separators, comma decimals, kg/lb/st, times after the date, junk lines) but rejects implausible numbers, future days, impossible dates, negatives and lines with no number. The last weigh-in of a day wins.
- **Dates are normalised before parsing** (`withIsoDate()`): if the Shortcut's Custom date format doesn't stick, the phone writes `01/10/2026, 12:00` instead of `2026-10-01 12:00`, so `dd/MM/yyyy` and `dd.MM.yyyy` are accepted (day first, as in the UK, unless only month-first can be valid) along with a 12-hour `AM`/`PM` start time. Impossible dates are still skipped, never guessed.
- **Sleep is different: Health has no "sleep last night" number,** only segments (Core, Deep, REM, Awake, In Bed…), so a night is the *sum* of its lines. Durations are read from whatever Shortcuts prints ("1 hr 5 min", "45 min", "7,5 h", a bare number = hours); Awake and In Bed segments are ignored by name (not counted as errors) so a forgotten filter can't inflate a night. A segment starting at 18:00 or later belongs to the *next* day (you wake up on it), and one that would land after today is silently dropped.
- **When a paste has several nights of timed segments, the oldest is left out (`partialDay`)** — with a single night nothing is dropped, since it can't be told from a complete one — because the Shortcut's date window can start mid-night and a short total would overwrite a good one — which is why the guide asks for sleep over the last *8* days against the others' 7. Pre-totalled lines with no start time are trusted as they are. A day whose segments add up to more than 24 h (overlapping data) is skipped and counted.
- `planHealthImport()` merges into existing entries: anything Health has nothing for is kept as logged, a 0 step count never wipes a typed number, unchanged days are skipped, and days that change existing values are flagged "updates". Health's sleep replaces a typed sleep figure for that day.
- If the clipboard can't be read (denied, dismissed, unsupported), the sheet falls back to a box you paste into by hand.

### Routines (`habits/routine.js`, `routine-sheet.js`, `step-editor.js`)

A habit may carry optional `note` and `steps: [{id, text, detail?, days?}]`; a habit with steps is a **routine**. A step's `days` (Monday=0…Sunday=6) limits it to certain weekdays; without it the step follows the routine. Pressing a routine opens its checklist instead of ticking it.

- **One rule keeps them consistent:** a routine is done on a day exactly when every step due that day is ticked. `setStepDone()` maintains it tick by tick; `toggleHabit()` (the week grid, Today) ticks or clears all of that day's steps; `updateHabit()` re-checks *today* after an edit. Use `toggleHabit`, not the low-level `toggleDone`, from UI.
- Step ids survive edits, so reordering or rewording steps keeps today's ticks.
- Personal routines are not in the repo (it's public for GitHub Pages): they're imported as a `life-backup` file. `.gitignore` excludes `*-backup-*.json` and `life-routines*.json`.

### Time of day (`habits/times.js`)

A habit may carry `timeOfDay`: `'morning'`, `'afternoon'` or `'night'`; with none it is **All day** — can be done at any point in the day (`'anytime'`, which is never stored). Today and Week group habits under those four headings in that order (`groupByTime()`: empty groups are left out, and habits keep their own order within a group), Today shows "N of M" done per group beside the overall summary, and the home screen's Habits card lists the day in the same order (`timeRank()`). Chosen with the **When** picker in the add/edit sheet; new habits start on All day.

- **It's only a label for organising the checklist.** It doesn't change when a habit is due, how streaks run, or when it can be ticked — a morning habit can still be ticked at night (and it backfills past days like any other).
- **No migration:** every habit made before this has no `timeOfDay`, which already means All day. Choosing All day again *removes* the field rather than saving `'anytime'` (`withExtras()` in `store.js`, same rule as `note` and `steps`).
- `ROW_CHECKS.habits` in `backup-format.js` accepts the field absent or one of the three and rejects anything else, via `isTimeOfDay()`. Additive, so `LIFE_VERSION` is unchanged and older backups import as they were.

### Weekly-target habits (`habits/streaks.js`)

A habit is either on **fixed days** (`days`, Monday=0…Sunday=6) or has a **weekly target**: `weeklyTarget`, 1–6 times in a Monday-to-Sunday week, on whichever days you like. Chosen with **Repeats** in the habit sheet (On certain days / Times a week); absent means fixed days, which is every habit made before it existed. A weekly habit stores `days` as every day (7 a week would just be every day, so the target stops at 6), so anything reading `days` still sees an any-day habit, and `ROW_CHECKS.habits` accepts the field absent or a whole number 1–6. Additive: `LIFE_VERSION` unchanged. `withExtras()` in the store enforces `days = every day` and removes the field again when you switch back to fixed days.

- **Ticking is the same thing:** a tick is still a `habitLogs` row (`habitId|day`), and a routine can have a weekly target too. Nothing about a day is "due" — any day from the habit's start can be ticked, today or backfilled.
- **Counted in the day's "N of M" only while the week still wants it** (`isDue()`): a weekly habit is due until its week's target is met, and stays counted on a day you ticked (so the tick that finishes the week doesn't make it vanish). After that it is still listed on Today with "Done for the week · 3 of 3", quietly, and left out of the count and the home block (which says "Week done" if that's all that's left). Extra ticks are allowed; progress is capped so it never reads "4 of 3".
- **Streaks count weeks in a row that hit the target** (`weeklyHistory()`): the current week counts once it's met, and being short *so far* doesn't break the run — an earlier short week does. Shown as "N weeks in a row" (home block: "4w"). Longest run likewise, in weeks.
- **A habit begun midweek is only asked for what its days could hold** (`weekTarget()`): started on a Friday, "3 a week" can't need 3 in the first three days, so that first week asks for `min(target, days left)`; every later week asks the full target. A week before the habit existed shows "—".
- **The week grid has no "missed" for a weekly habit** (nothing was due on a given day): a ticked day is `done`, an unticked past or present one is `free` (an outlined circle, still tappable to backfill), later days `future`.
- **Fixed-day habits are untouched.** `tests/habits-streaks.test.mjs` holds the current code to verbatim copies of the old daily streak and week-cell functions over 4,000 random habits.
- **The Sunday review** counts a weekly habit as its ticks against its target (a week still to finish simply shows short of it), not as per-day misses.

### Today (`life/home.js`)

The home screen is a live summary of the day, one block per section, each with its most likely next action. It reads through the sections' own stores and maths (`nutrition/store.js`, `habits/streaks.js`, `body/stats.js`, `computeProgress()`), so its numbers always match the sections. Habits can be ticked in place. Buttons deep-link with a route action — `#/gym/workout`, `#/gym/workout:<plan id>`, `#/nutrition/log`, `#/body/log`, `#/habits/new` — handled by each section's `enter(action)`; the action is dropped from the URL once used. Today re-renders when the app comes back to the foreground, so it rolls over to a new day.

**The Gym block suggests your next plan** (`nextPlan()` in `gym/js/next-plan.js`, pure and Node-tested): "Up next: Pull Day · not done yet" with a **Start Pull Day** button that starts it in one tap (`#/gym/workout:<plan id>` → `startPlan()` in `gym/js/app.js`), and a quiet "Other plans or a quick workout" link to the Workout tab. The next plan is one not yet done *this week* (Monday to Sunday, by local day), and of those the one done longest ago (never done = longest ago); once every plan has been done this week a new round starts from the one done longest ago; ties go to the order plans are listed in; a plan opted out of the weekly plan is only suggested when none is in it; quick workouts count for no plan. **It isn't offered once today is trained or the week's target is met** — then it is the old quiet "Start another workout". A link to a deleted plan opens the Workout tab rather than starting an empty session, and one while a workout is open is refused with the usual message and replaces nothing.

**Weekly review (Sundays):** on Sunday Today opens with a "Your week" card (`life/review.js`, `reviewCard()` in `home.js`): one row per section that has something to say about Monday-to-Sunday, each opening that section. It is the week *so far* on any other day it's built for, but it is only shown on Sunday (`isReviewDay()`); a card that vanished at midnight is the trade-off for not having a dismiss to maintain, and there is no notification (a home-screen web app can't send one without a push server).
- **It reads, it doesn't recount.** Gym's sessions/target/sets/kg moved/PRs are `computeProgress().currentWeek` itself; "lifts at target" is the same `entryMetBar()` the XP uses. Body is `weeklyAverages()` (this week against the nearest earlier week that has a weight), habits use `weekCells()`, nutrition `dayTotals()`.
- **Gaps are gaps, never zeros:** Body and Nutrition average over the days that *have* the number ("Logged 5 of 7 days · 1,780 kcal a day" is over those 5), habit days that haven't happened yet this week aren't due, and a section with nothing this week — or Gym with no workouts ever — is left out rather than shown empty. If every section is empty there's no card.
- **Tasks, Videos and Inbox aren't in it on purpose:** a ticked task is deleted 24 hours later, so "tasks done this week" would be wrong by Thursday.
- The week's food is read with `loadDays()` (nutrition store), which leaves the day the Nutrition screen is showing alone, and only on Sundays. Numbers keep to their units with non-breaking spaces so a wrapped line never starts with a bare "kg".

**Weekly weigh-in reminder:** from Saturday 12:00 until that weekend (Sat or Sun) has a Body weight and a steps entry, Today shows a card linking to `#/body/log` (`weeklyLogReminder()` in `body/stats.js`, pure and tested). A home-screen web app can't schedule notifications without a push server, so the actual phone alert is a repeating calendar event: `life-weekly-weigh-in.ics`, generated locally and git-ignored (`life-*.ics`).

### LifeDB (`life/db.js`)

Storage for every section **except Gym**, which keeps its own `GymTrackerDB` (its data and backups predate Life, so it was deliberately left alone). Stores: `foods`, `nutritionEntries` (index `day`, a local `YYYY-MM-DD`), `settings` (v1, Nutrition); `habits` and `habitLogs` (v2, Habits — a log's id is `habitId|day` and its presence means done; a habit's `days` are Monday=0…Sunday=6); `bodyEntries` (v3, Body — keyPath is the local `day`, so one record per day; any of `weightKg`, `sleepHours`, `steps` may be `null` = not recorded, never a fake 0); `routineTicks` (v4 — `habitId|day` → the step ids ticked that day); `videos` (v5, Videos — free-text `topic`, no separate topics table); `tasks` (v6, Tasks — index `date`; `time` is a local `HH:MM` or `null` for all-day; `calendarSequence` tracks the `.ics` export version); `journalEntries` (v7, Journal — keyPath is the local `day`, one check-in per day; `mood`/`energy` 1–5 or `null`, optional `note`); `notes` (v8, Inbox — `text`, optional `pinned`, `createdAt`/`updatedAt`); `savedMeals` (v9, Nutrition — `name`, `items`, `createdAt`, optional `lastUsedAt`). Upgrades are additive (`contains` guards in `onupgradeneeded`), so existing data survives a version bump. A generic get/getAll/byIndex/put/delete wrapper; each section keeps its record shapes and helpers in its own `store.js`. Call `await lifeDb.init()` before use (idempotent). **Both databases yield to a newer version:** each connection sets `onversionchange` to close itself and fire `life-db-outdated` on `window` (`life/updates.js` answers with the "A new version is ready · Reload" banner), so an upgrade is never left "blocked" by an older copy of the app that is still open — the new page used to fail to start with "close other tabs running this app" while the old one sat there. The old page can no longer use its closed connection, hence the reload prompt. Checked for real by requesting a higher version from the page, which reports `blocked` on the old code and goes straight to `upgrading → opened` on the new.

### Journal (`journal/insights.js`, `store.js`, `journal.js`)

A short daily check-in: **mood** and **energy** on 1–5 scales with words (Rough…Great, Drained…Energised), then text boxes for **Dreams**, **Morning**, **Afternoon**, **Night** and a general **Note** (`NOTE_FIELDS` in `insights.js`; each is an optional string on the entry under its id, so no migration — older entries simply lack them, and `ROW_CHECKS.journalEntries` accepts each absent or text). Mood stays one per day, so the patterns and Today card are unchanged; a day with text in any box counts as a check-in (`hasContent()`), and lists show `entryPreview()` (the note, else the first part of the day written about). One entry per local day; the day bar steps back to fill one in, and tapping a chosen level again clears it. Null means not recorded — never a fake middle value — and a day left with nothing in it is deleted, not kept as an empty row. Every box autosaves together while typing (debounced) without redrawing the card, so the keyboard keeps its place; mood/energy taps carry every box's current text, so text typed a moment before a tap is never lost. Anything that saves an entry from elsewhere (Today's mood buttons) must pass the whole entry through, or it would wipe these.

- **Patterns** (`insights()`): mood on days with a finished workout vs without (from Gym), and energy after 7+ hours of sleep vs less (from Body's `sleepHours`, keyed by the day you woke up). Last 60 days only; each sentence appears only once **both** sides have `MIN_DAYS` (4) entries, days with no sleep figure are left out rather than counted as short nights, a gap under 0.3 is "about the same", and it says "a pattern, not proof". Gym is read straight from its in-memory workouts, so the route waits on `gymBoot` like Body's.
- **Home card**: until today has a mood, five buttons save one with a single tap; after, it shows the mood with energy and the start of the note.
- Colour `--journal` is a calm slate (not ochre, which read as the `--warning` status colour); checked ≥4.5:1 for text on it and as text, in both modes.

### Inbox (`inbox/organize.js`, `store.js`, `inbox.js`)

Quick capture for ideas and things to remember: a box at the top (Save stays disabled until there's text), a search field, tag chips, and the notes — pinned first, then most recently changed. Tap a note to edit it, pin it, **Make it a task**, or delete it.

- **Tags are `#words` in the text, never a stored field** (`parseTags()`): letters, digits, `-`, `_` in any language, at the start or after a space — so "C#" and a URL's `#fragment` aren't tags. Case doesn't split a tag (#Gym and #gym are one, shown as first written). Editing the text is the only way to change tags, so they can't drift; a tag no note uses any more disappears, and drops out of the filter.
- **Search** matches every word, case-insensitively, and combines with the tag filter. The capture box and search field are built once per visit and only the chips and list redraw (`refreshList()`), so saving a note or typing a search never loses the keyboard.
- **Make it a task** calls Tasks' own `addTask()`: the first line becomes the title (cut to 80 characters), the whole note goes in the task's note when there's more to it, due today with no time (change it in Tasks). The note stays in the Inbox.
- `updatedAt` only moves when the text changes, so pinning doesn't reshuffle the list. `#/inbox/new` (the home card's "Jot something down") opens with the cursor in the capture box.
- Colour `--inbox` is olive — the hue furthest from every other section and status colour that still clears ≥4.5:1 both ways in both modes.

### Videos (`videos/organize.js`, `store.js`, `oembed.js`)

A watch-list, not a fixed-category browser: a video's `topic` is free text, so a group appears the first time something is filed under it. This is also the section a video ends up in when links arrive over chat rather than typed into the app — sorted into a topic by hand, same as any other addition.

- **Grouping is case-insensitive** (`groupByTopic()`/`existingTopics()` in `organize.js`): "Gym" and "gym" are the same topic, shown under whichever casing was used first. `Uncategorised` (an empty topic) always sorts last. Inside a group, unwatched videos come first (oldest added first — a backlog worked through in order), then watched ones (most recently watched first).
- **Renaming a topic** (`renameTopic()` in `store.js`) updates every video that used it — there's no separate topics table to keep in sync.
- **YouTube links** get a thumbnail (`thumbnailUrl()`, parsed from any common URL shape — watch, `youtu.be`, Shorts, embed) and, when a link is pasted into the add sheet, a best-effort title fetch from YouTube's oEmbed endpoint (`oembed.js`, no key, times out quietly). Neither is load-bearing: a failed lookup just leaves the title for you to type, and a non-YouTube link still saves fine with no thumbnail.
- Tapping a video's title/thumbnail opens the real link in a new tab (`target="_blank" rel="noopener noreferrer"`) — there's no embedded player to keep working offline or in sync with the source.
- **Videos sent over chat** (there's no live connection from here into the person's phone) go into a `life-backup`-shaped file with just `life.videos` set — the same mechanism as `life-routines*.json` — for them to bring in via Backup → Import. `.gitignore` excludes `life-videos*.json` alongside the routines pattern.

### Tasks (`tasks/organize.js`, `store.js`, `ics.js`)

A due-date to-do list — not a browsable library (that's Videos, and not something you tick for a streak, that's Habits): a task has one date at a time, and once it's `done` when it was due stops mattering. A chore that comes round (bins, rent, a yearly renewal) can **repeat**, below.

- **Repeating tasks** (`tasks/recurrence.js`): a task may carry `repeat: { unit: 'day'|'week'|'month'|'year', every, anchor }`; the sheet's **Repeats** offers Never, Every day, Every week, Every 2 weeks, Every month, Every year (an imported repeat the sheet has no preset for gets its own option, so editing never silently changes it). **A repeating task is never "done":** ticking it (`completeTask()` in the store) moves it to its next date — the first occurrence strictly after *both* its due date and today, so ticking early moves it a whole step on and ticking weeks late skips the occurrences missed rather than leaving a pile of overdue copies — and says "Done. Next: Thu 12 Nov". There is no Done box in the sheet for one, and giving a done task a repeat un-dones it.
  - **Every occurrence is counted from the `anchor`** (the date the series started), never from the previous one, so a monthly task on the 31st goes 31 Jan → 28 Feb → 31 Mar → 30 Apr (stepping from the clamped date would drift to the 28th). Saving unchanged keeps the anchor; re-dating the task by hand, or changing its rule, re-anchors it to the new date. A yearly task on 29 Feb is 28 Feb in a common year.
  - **The `.ics` gets an `RRULE`** (`rruleFor()`), so an exported repeating task is a repeating calendar event starting on its current date. The 29th–31st monthly (and a 29 Feb yearly) are written as "the last of the days 28…N that exists" (`BYMONTHDAY=28,29,30,31;BYSETPOS=-1`), which is exactly the app's clamp; a plain monthly rule would make a calendar skip the short months. **That form is correct by RFC 5545 but wasn't tried in Apple Calendar** — the daily, weekly, monthly (1st–28th) and yearly rules are the common ones.
  - A repeating task is always open, so Today's count of tasks due includes it (as it does any task with a future date). `ROW_CHECKS.tasks` accepts `repeat` absent or well-formed (`isValidRepeat()`); additive, `LIFE_VERSION` unchanged. No undo for an accidental tick: edit the date back.
- **Bucketing** (`groupTasks()` in `organize.js`) is by how soon a not-done task is due — Overdue, Today, Tomorrow, This week (≤7 days out), Later — each sorted soonest-first, timed tasks before an all-day one on the same date. Done tasks are never in a date bucket; they're returned separately, most-recently-completed first, since *when* a finished task was due isn't the point any more.
- **Ticked tasks are deleted 24 hours after they were ticked.** `loadTasks()` in `store.js` clears them (`isDoneExpired()` in `organize.js`) whenever the data is read — the Tasks screen and Today both go through it, and there's no timer because a home-screen app is usually closed. It's a real delete, not a hide, so a calendar event already exported stays in Calendar. Un-ticking clears `doneAt` and restarts nothing: it's simply not done any more. A done task with no usable `doneAt` (or one in the future, from a clock set back) is kept rather than guessed at.
- **The calendar export is why this section exists.** A home-screen web app has no API to write into Calendar directly. **Calendar isn't a registered Share Sheet target on iOS** (confirmed on a real phone — sharing an `.ics` file offers Mail/Messages/Files, never Calendar), so `addToCalendar()` in `tasks.js` doesn't share it: it clicks a same-window `<a href="blob:...">` (no `target`) pointing at a `text/calendar` blob, which iOS intercepts before any navigation actually happens and shows its own "Add Event" screen for instead — the same mechanism as a `tel:`/`mailto:` link, and the trick behind every "Add to calendar" web button. Two things this went through and rejected, both confirmed on a real phone: **`window.open()` instead of a same-window click** — it doesn't get the interception at all, it just opens a second tab that sits there failing to render the resource, since that's a *new* browsing context and iOS's calendar-mime sniffing only watches top-level navigation of the current one; and **a `data:` URI instead of a `blob:` one** — WebKit silently blocks top-level navigation to a `data:` URI outright (an anti-phishing measure, since `data:` links can spoof a real page), so the click was simply a no-op with no error and no visible effect. `shareCalendarFile()` (`life/share.js`'s share-or-download) is kept as an explicit secondary "Share the file instead" link in the sheet, for whenever the direct-open convention doesn't apply — Files → tapping the saved `.ics` still reaches Calendar's own add screen, just as a second tap.
- Each task's own id becomes the event's stable UID (`calendarUid()` in `ics.js`), and `calendarSequence` (bumped by whichever export path is used, saved in the task) is the event's SEQUENCE — so exporting again after editing a task updates the same calendar entry instead of creating a duplicate, which is what most calendar apps (Apple's included) do with a repeated UID and a higher SEQUENCE.
- **Timing matters for both export paths**: the `.ics` text and the anchor click/`File`+`shareOrDownload()` call must happen with *nothing else awaited first* — the same iOS constraint Backup's export works around (see below) — or Safari treats the call as not user-initiated and silently ignores it. The `calendarSequence` bump is saved to LifeDB right after either path runs, via `recordCalendarExport()` — there's no signal back from either (same as a `tel:` link) to confirm Calendar actually opened, only that the tap happened. The blob URL is revoked a few seconds later, not immediately, so a slower hand-off doesn't race the revoke.
- DTSTART/DTEND use floating local time (no `Z`, no `TZID`) for a timed task, and `VALUE=DATE` (with an exclusive, next-day DTEND) for an all-day one — the same choice already made for the weekly weigh-in reminder, chosen so a DST change can't shift it.
- A brand-new task's sheet, once saved, **reopens itself in edit mode** for the task just created (rather than closing), so Add to Calendar is available without a second trip back into the list.

### Backup (`life/backup.js`, `life/backup-format.js`)

Opened from the ⚙️ on the Life home. One `life-backup` file wraps the Gym export whole (`gym`, exactly what Gym's own Export writes) plus every LifeDB store (`life`); `lifeDb.exportAll()` / `importAll()` do the Life side. Gym's own Export/Import in its settings still works unchanged, and a bare Gym backup (the pre-Life `gym-tracker-backup` format) is still accepted on import, restoring only Gym.

- **Import merges** (same as Gym's): rows are `put` by key, so a matching ID or day is replaced and nothing is deleted. `inspectBackup()` validates the *whole* file before anything is written — one damaged row rejects it — and `lifeDb.importAll` is a single aborting transaction. Gym and Life are two databases, so the pair isn't atomic; a Gym failure after Life succeeded is reported as such.
- **When you add a LifeDB store,** add it to `LIFE_STORES` (with its key field) and a row check in `ROW_CHECKS` in `backup-format.js`, or it silently won't be backed up. Bump `LIFE_VERSION` only for a change older Life versions can't read.
- `lastBackupAt` is a device setting: it lives in LifeDB `settings` but is excluded from export and import (`DEVICE_SETTINGS`), so restoring an old backup can't make a fresh one look stale.
- **Export** builds the file when the sheet opens (sharing must start straight from the tap on iOS), then hands it to `shareOrDownload()` (`life/share.js`) — the Web Share API where there is one (on iPhone, "Save to Files", AirDrop…), a download otherwise. A cancelled share isn't recorded as a backup.
- The home screen nudges (`needsNudge`) when there's data and no backup for 7+ days (`NUDGE_AFTER_DAYS`), or never. `hasAnyData()` counts every `LIFE_STORES` store but `settings`, so a new section is covered automatically (a hand-kept list used to miss Journal and Inbox).
- **A failed save must say so.** `life/life.js` asks the browser for persistent storage once at boot (`navigator.storage.persist()`, best effort — iOS may decline) and listens for `error`/`unhandledrejection`, toasting only when `isStorageError()` says it's a storage failure, at most once per 30 s. Gym's `persist()` (called from ~16 places, mostly un-awaited) catches its own errors and toasts through the same gate rather than letting them vanish; `finishWorkout()` saves a *copy* of the session and only clears `session` once that succeeded, so a failed Finish leaves the workout open to retry. Don't add generic "something went wrong" toasts — they'd fire on errors that have nothing to do with the user's data.
- After an import, `reloadGym()` (in `gym/js/app.js`) re-reads Gym's data; the other sections reload on every `enter()`.

**Weight unit:** Body follows Gym's global kg/lb setting (`getUnit()` in `gym/js/units.js`, loaded while Gym boots). `life/life.js` starts `bootGym()` before the first route and Body's `enter` waits on it, so loading straight onto `#/body` can't read the unit too early. Weight is stored in kg and converted only at the display/input edge, same as Gym.

### Gym section internals

Everything below lives in `gym/js/`.

### Data layer: `db.js` + `store.js`

`js/db.js` wraps IndexedDB (`GymTrackerDB`) behind a single `Database` class (singleton export `database`). It owns the schema and version migrations (`DB_VERSION`, bumped in `onupgradeneeded`) across five object stores: `exercises`, `templates`, `workouts`, `media` (blobs kept separate from exercise records so listing the library never drags video into memory), and `settings`.

`js/store.js` holds an in-memory mirror of the DB in a plain `state` object (`exercises`, `templates`, `workouts`, `activeWorkout`). There is **no reactivity** — after any mutation via `db.js`, the calling code must explicitly re-run the matching `loadX()` in `store.js` to refresh `state`, then call the relevant module's `renderX()` to redraw. `bootstrap()` in `store.js` is the top-level data init, called once from `bootGym()` in `app.js`.

### Module shape

Every feature area (`library.js`, `templates.js`, `workout.js`, `history.js`, `records.js`, `settings.js`) follows the same pair of exports: `initX()` wires event listeners once at boot, `renderX()` tears down and rebuilds that tab's DOM from current `state`. `gym/js/app.js` (`bootGym()`) calls every `initX()` then does the first render pass; `life/life.js` calls it once at startup.

`js/workout.js` is the largest module: it owns the active-workout session state machine (start/finish/discard), the elapsed-time stopwatch (pauses automatically once every set is ticked, driven by a deadline timestamp rather than a decrementing counter so it survives backgrounded-tab throttling), a hand-rolled drag-to-reorder for exercises (pointer events, FLIP-style animation, no library), and timing the "exercise added" entrance animation to when the exercise picker sheet actually closes rather than when the DOM node is inserted (the picker is full-screen, so animating on insertion would play invisibly behind it).

### Rep schemes (`gym/js/prescription.js`, `guidance.js`)

What a plan entry starts with depends on the *kind* of lift, not one flat default (`DEFAULTS` in `db.js` is now only the fallback for old data and the v1→v2 migration). `exerciseRole()` sorts an exercise into `main` (heavy compound: squat, bench, RDL, pull-up, barbell row, DB shoulder press), `secondary` (machine/dumbbell compound) or `isolation` — by id for the seeded library, and by a name/muscle-group/equipment guess for custom exercises (Biceps/Triceps/Core and names like "curl", "raise", "fly", "extension" are isolation). `PRESETS` maps each role to `{sets, reps, restSeconds, rir}` under three schemes: **Strength**, **Strength + physique** (the default: 4×6 / 3×10 / 3×15, rest 180 / 150 / 120s) and **Hypertrophy**.

- **Some lifts nudge their role's numbers** (`ADJUST` in `prescription.js`, keyed by exercise id, applied by `prescriptionFor()` under every scheme): deltas for `reps`/`restSeconds`/`rir` and a `maxSets` cap, so a deadlift is never more than 3 sets at 5 reps and 3 RIR, a seated calf raise goes to 20 reps, curls sit at 12, and safe machine/cable isolation lifts can go to 0 RIR. Reps snap to a top the range text already knows (3, 4, 5, 6, 8, 10, 12, 15, 20) and only isolation work goes below 1 RIR. **Every new stock exercise should get a role (if the name guess would be wrong) and, if it doesn't behave like its role, an `ADJUST` entry.** Plans saved earlier keep their own numbers; the Rep scheme picker re-applies these.
- **Rest is always 2–3 minutes** (`REST_MIN`/`REST_MAX` 120–180 s, `clampRest()` in `prescription.js`): the presets sit inside it, both rest steppers are bounded by it, and everything that reads a saved rest (`loadTemplates()`, `entryFromTemplate()`, `exerciseBlock()`, `startRest()` from a ticked set) clamps it, so plans and sessions saved earlier come out in range without a migration. The live rest bar's −15s/+30s/Skip are in-the-moment overrides and aren't limited.
- **Every listed exercise shows what to do with it** — not only ones already in a plan. `recommendationFor()` (`prescription.js`) is `prescriptionFor()` with the rep range and RIR worded as a workout words them (`repRange()`/`rirLabel()` in `guidance.js`), and it appears as the compact line "3 × 6–10 reps · ~1 RIR" (`.rec-line`) on every Library card and Add Exercise picker row, and in full (sets, range, RIR guidance, rest) under **Recommended** in the exercise details. It is derived, never stored, so it can't drift from what a plan entry or a mid-workout exercise starts at — it *is* that. Live workouts show the same "Work in the … rep range / Target … RIR" hint for **every** exercise (`entry.targetReps`/`targetRir`), not only those from a plan. The swap sheet shows it too, as "Sets to …" (see Swapping an exercise) — a swap applies the new exercise's numbers. Saved plans keep their own numbers.
- `reps` is still the *top* of the range; `guidance.js` shows the range (6 → 4–6, 10 → 6–10, 15 → 10–15). Don't add a second "range" field.
- The plan editor's **Rep scheme** picker overwrites sets/reps/rest/RIR on every exercise in the draft (notes untouched) and records `draft.preset` on the template, so exercises added later start from that scheme. Like every edit there, nothing persists until Save. Plans saved before this have no `preset`, so none shows as active and new exercises use the default scheme.
- An exercise added mid-workout (`entryFromExercise()` in `workout.js`) uses the default scheme too. Existing plans are never rewritten automatically — they're the user's data.

### The progression bar and plate maths (`gym/js/progression.js`, `plate-math.js`)

**One rule decides "met the bar"**: `entryMetBar(entry, { live })` — every working set at the entry's `targetReps` with at least `targetRir` left. It answers two questions that used to be separate hand-written copies, and the options keep each answer exactly what it was: by default (a **saved** workout — XP's "exercise at target", and the progression suggestion) only done working sets count and a set with no RIR counts as 0 left; with `{ live: true }` (the open workout's "Ready to progress" badge) every non-warm-up set must be ticked and a set with no RIR value fails. `progress.js` and `workout.js` both call it, so the XP can't drift from the badge. **Don't change the default's behaviour without meaning to change everyone's XP:** `tests/progression.test.mjs` compares it against verbatim copies of the two old functions over 50,000 random entries each (missing/`null`/`NaN`/string fields included), and was checked to fail when the rule is deliberately broken.

- A new entry also records **`targetSets`** (the working sets the plan or prescription asked for), fixed at session start like `targetReps`/`targetRir`, because sets can be added or removed mid-session and "did you do what was asked" must be judged against what was asked. Older entries simply don't have it.
- **The progression suggestion** (`suggestNext()` in `progression.js`, shown by `exerciseBlock()`): a quiet line under the "Ready to progress" badge — "At 60 kg every set hit 6 reps. Try 62.5 kg." with a **Use 62.5 kg** button — or, after repeated misses, "At 100 kg, the last 3 sessions fell short of 6 reps a set. Try a lighter 90 kg to rebuild." It only ever *offers*: nothing changes until Use, and it goes away once any working set is ticked or once the heaviest set still to do is already at (or past) the suggestion. Computed with the set list (`refreshSets()`), so adding/removing a set refreshes it, and **it follows the saved workouts too**: each block registers a refresher (`suggestionRefreshers` in `workout.js`, run on the `workouts` event like the "last N" captions) so deleting or editing a session in History, or restoring a backup, mid-workout redoes the hint *in place* (no rebuild, so half-typed notes, ticked sets and scroll are untouched). Refreshers for blocks that have been rebuilt or removed are dropped as they're met.
  - **Which history counts:** sessions of the *same exercise* (by the lift actually done, not the plan slot — a swap-in counts, a swap-away doesn't) at the **same `targetReps`** as now, so a 4×6 Push day never inherits a 3×12 Upper day's result; past entries with no recorded `targetReps` can't be judged. The newest comparable session must be **under 42 days old**. Assisted exercises (more weight = easier) and unloaded bodyweight (nothing to add) are skipped.
  - **Progress:** the newest comparable session met the bar (`entryMetBar`) **over its whole set count** — a saved workout keeps only ticked sets, so "every set hit 6" is cheap if two of four were done; it uses that entry's `targetSets`, or the set count being asked now for sessions saved before `targetSets` existed. Step by lift: main lower-body 2× the coarse step (5 kg / 10 lb), other main and secondary lifts 1× (2.5 kg / 5 lb), isolation the fine step (1.25 kg / 2.5 lb) except dumbbells, which only come coarse. A **barbell** is rounded to what the plates can build on the remembered bar (`getBarWeight()`), and never lands on the weight it started from.
  - **Deload:** the last three comparable sessions all fell short *and* the newest isn't a new best (estimated one-rep max; weight × reps where sets are too high-rep for the estimate): about 10% off, rounded **down** (to the plates on a barbell, to the fine step elsewhere), and only if that really is lighter.
  - **"Use" moves the sets together so the heaviest lands on the target** (`shiftToTop()`), not "add the step to what's on screen": new sessions seed their weights from the last session of that lift under *any* plan, so after a light Upper day a Push day starts well below the number being suggested. A pyramid stays a pyramid; unticked working sets only, never warm-ups, one save.
  - Wording names the weight ("At 60 kg…") rather than saying "last time", because the set rows already show a "Last time" line for the most recent session of any plan, and the two would read as contradicting.
- **Warm-up ramp** (`gym/js/warmup.js`, the **Ramp** button beside **+ Warm-up**): `rampFor({ entry, workingKg, unit, bar })` returns the warm-up sets to put ahead of the heaviest working set — main lifts 40/60/80% for 8/5/3 reps, secondary 50/75% for 8/5, isolation 60% for 10 (an explicit table, not "the top N of 40/60/80", which would make a lone isolation warm-up 80% of the work). On a barbell each weight is what the plates can build and never under the bar; elsewhere it rounds to the fine step; sets that round to the previous weight, or to the working weight or above, are dropped, so a light bar gets a short ramp. Assisted and bodyweight lifts get none. The button shows only while it can help (a weight to ramp to, no warm-up yet, nothing ticked) and re-checks whenever a weight or tick changes, so it reads what **Use** just set. `insertWarmups()` adds them all and saves once; the single **+ Warm-up** goes through it too. Warm-ups stay out of every count, as before. The block's button row (`.block-actions`) sizes to its labels and wraps instead of squeezing four buttons.
- `plate-math.js` is the pure half of the plate calculator, in **display units** (kg *or* lb, never converted — a 45 lb plate isn't 20.4 kg): `PLATE_SIZES`, `DEFAULT_BAR`, `platesPerSide()` (unit is required — no default) and `roundToLoadable(target, bar, unit, 'nearest'|'down'|'up')`, which snaps to what the plates can build (bar + whole multiples of the smallest pair: 2.5 kg, 5 lb), never below the bar. `plates.js` keeps only the sheet UI and the remembered bar weight.

### Saving a workout as a plan (`gym/js/plan-from-workout.js`)

The History detail sheet has **Save as a plan** beside Delete: a workout you improvised (or liked) becomes a plan to repeat, via the ordinary plan editor, opened *pre-filled* (`openTemplateForm(null, seed)` — still a new plan, nothing saved until Save, name left blank for a quick workout so you choose one). `planFromWorkout()` is pure and Node-tested: exercises keep the order they were done in; `sets` is the number of logged **working** sets (warm-ups are a ramp-up, not part of a plan); `reps` is the rep target the entry was held to (`targetReps`, which *is* a plan's "top of the range"), else the most reps you did; `rir` is `targetRir` (0 is a real target), else the RIR you most often logged (the lower on a tie), else 2; rest is clamped to the 2–3 minutes the app allows. An exercise with no logged working sets, or no longer in the library, is left out, and a workout with nothing left (a note-only session) gets no button. Weights aren't stored in plans, so none are carried over — they seed from what you last lifted when the plan is started.

### Swapping an exercise (`gym/js/alternatives.js`, `swapExercise()`/`applySwap()` in `workout.js`)

The **Swap** button (beside Edit) on an exercise in a live workout opens `#swap-modal`: substitutes that train the same muscle in a similar way, closest first, each with a one-line note on what changes, plus **Browse all exercises** (the full picker) for anything not listed. `alternativesFor()` is pure.

- **Each seeded exercise has a hand-written list** (`CURATED`) of at least two substitutes, checked by `tests/gym-data.test.mjs` to only reference real exercises in the *same muscle group*. A list may be left empty where the library has no honest equivalent — the sheet says so rather than suggest a bad match. Where a swap trades a compound for a single-joint lift (leg extension ↔ squats, RDL ↔ leg curls, close-grip bench ↔ triceps isolation) the note says it. **Adding a stock exercise to `seed.js` means giving it a `CURATED` entry (and adding it to existing lists where it fits), and a role in `ROLE_BY_ID` if the name/equipment guess in `prescription.js` would get it wrong** — e.g. a heavy lift in a small muscle group like close-grip bench (Triceps) would otherwise be classed as isolation.
- **New stock exercises reach existing installs automatically:** `seedExercises()` inserts any default that's missing on every boot and never touches a row that exists, so hand-edited stock notes and the user's own exercises are safe. (It also means deleting a stock exercise doesn't stick — it comes back next launch.)
- **Custom exercises** (no list) get same muscle group *and* same kind of lift (`exerciseRole()`); they also appear after the hand-written ones on a stock exercise's list when they match. No muscle group → no suggestions.
- **`applySwap()` keeps the slot's set count but gives the new exercise its own reps, RIR and rest** (`targetsForSwap()`): what suits a heavy barbell press doesn't suit a cable fly, and `targetReps`/`targetRir` are also what "ready to progress" is judged against, so they must be the new exercise's. They come from the plan itself when the plan has that exercise — notably when swapping **back** to what it asked for, which restores the plan's own saved numbers — and otherwise from `prescriptionFor()` in the plan's rep scheme (`template.preset`, else the default). Each working set is re-seeded like starting it from a plan: weight and RIR from what was last lifted on the new exercise (blank / the target if never), reps at the target. Ticked sets were done on the old exercise, so it asks, then clears them rather than crediting them to the new one. The swap sheet shows "Sets to 6–10 reps · 1–2 RIR" on each option so the change is no surprise.
- **Notes:** every exercise block in a live workout has both a *Note for next time* (`entry.note`, carried to the next session) and a *Plan note*. The plan note is bound to the template's slot when there is one — a swapped-in exercise uses the slot of what it replaced (`swappedFromId`) — and otherwise (quick workout, exercise added mid-session) is kept on the workout entry as `entry.planNote`, cleared on a swap since it was about the old exercise.
- The entry records `swappedFromId`/`swappedFrom`, shown as "Swapped from …" and offered first in the sheet as the way back. The plan itself is never changed — next session it still asks for the original.

### Weekly check-in (`checkin.js`, `checkin-derive.js`)

On the History tab: a handful of numbers reviewed once a week and filed under that week's Monday (`checkins` store in `GymTrackerDB`): body weight, waist, average steps, average protein, sleep/energy (1–10) and a note, with the weight trend against the previous check-in. Sessions and PRs are counted from workouts, never typed.

- **Weight, steps and protein are pre-filled, not asked for twice.** Opening the form reads the week from Body (`bodyEntries`) and Nutrition (`loadDays()`), and `deriveCheckin()` (pure, Node-tested) averages them **over the days that have the number** (a day with no weigh-in or no food logged is a gap, never a zero; nothing after today; zero or missing isn't a reading). Weight is to one decimal, steps and protein whole numbers.
- **Only blank fields are filled, and what you saved is never overwritten** (`fillsFor()`): reopening a saved check-in after Body changed leaves your figures alone, while a field that was blank in it gets the current figure. Each filled field's hint says where it came from ("Filled from Body: average of 2 weigh-ins. Change it if you like."); you can still change it, and nothing is stored until Save.
- **The stored shape is unchanged** (so history, the trend and backups are untouched). Waist and sleep/energy have nothing to derive from and stay blank ("recorded as blank, not as a real zero"). If Body or Nutrition can't be read, the form just opens blank as it always did.
- `openCheckinForm()` is async for that read; it is called only from the History card.

### Lift goals (`goals.js`, `goals-ui.js`)

A goal is a lift target — "Bench Press 100 kg", "Squat 140 kg × 3": `{ id, exerciseId, exerciseName, targetKg, reps (1–12), createdAt }`, kept as the Gym setting `goals` (`loadGoals()`/`saveGoals()` in `store.js`, emitting `goals`), so backups carry it with no schema change and every import path reloads it. Shown as a **Goals** card at the top of the Records tab (tap a goal to edit or delete it), a "Goal 100 kg · 90% there" line under that exercise's name in a live workout (repainted in place on `goals`/`workouts`), and a "✅ Goal reached" line in the summary sheet of the workout that reaches it (passed to `showWorkoutSummary()` as `goalsReached`, which always counts as worth showing the sheet — it returns as soon as the sheet opens, so a toast after it would be covered by it).

- **Reached is a real set, never an estimate**: a logged working set (`isLoggedWork()`) at or above the target weight for at least the target reps; the *earliest* such set is when it was reached, worked out from history every time (never stored), so editing or deleting a workout in History can un-reach it. An estimated max above the target doesn't count — "bench 100 kg" isn't done until 100 kg has been on the bar.
- **Progress** is the best estimated max (`estimateOneRepMax()`, the Records cards' estimate) over what the target set represents (`targetEstimate()`: Epley at 0 RIR), held at 99% until it's really reached, so the bar moves every session without lying.
- Matched by the exercise actually done (`entry.exerciseId`), not the plan slot — a goal is about a lift. The card lists open goals first, closest to done at the top, then reached ones.
- The sheet's exercise comes from the shared picker; a new goal's target starts a little above the best estimated max on a round number, until one is typed.

### Lift history (`lift-history.js`, `lift-chart.js`, `lift-sheet.js`)

Tapping a card on the **PRs** tab (or pressing Enter on it) opens `#lift-modal`: that lift over time. A chart of one reading at a time — **Top weight**, **Est. 1RM** or **Volume** (weight × reps, summed) — over **3 months**, **1 year** or **All**; four plain facts (sessions, best set, best estimate, first → latest top weight); and the last ten sessions. `lift-history.js` is pure and tested in Node (`liftSessions()`, `metricPoints()`, `pointsInRange()`, `liftChartLayout()`, `liftStats()`); `lift-chart.js` draws the SVG the way Body's charts are drawn (createElementNS, classes in `gym.css`); `lift-sheet.js` is layout and wording.

- **A session is a workout the lift was done in**, from logged work only (`isLoggedWork()`: ticked, not a warm-up, with a weight), exactly as Records counts it; an exercise listed twice in one workout is one session, two workouts in a day are two. The top set is the heaviest (a tie goes to more reps).
- **No estimate is not zero.** A session whose sets are all too high-rep for Epley (over 12 effective reps) has no `e1rmKg`; it is left off that chart, never drawn at 0, and the Est. 1RM button is disabled when fewer than two sessions have one. The sheet opens on Est. 1RM when it can draw, otherwise on Top weight (so a 20-rep calf raise starts on weight).
- **A ring marks a new best** — a session that beat everything before it *for the reading being shown*; the first session never is. It is a shape, not only a colour.
- **The value axis doesn't start at zero** (a 10 kg gain would be a hair's breadth from zero), is padded, and never collapses: a lift that hasn't moved draws a flat line, and a very small change is kept small rather than stretched to the full height (the axis spans at least ±2.5% of the value).
- The ranges count back from today (`3m` = 91 days, a point exactly at the edge is in); "All" starts at the first session.

### Strength map (`strength.js`, `strength-standards.js`, `body-shapes.js`, `body-map.js`)

At the top of the Records tab, a front and back figure with each muscle shaded by how strong it is for **this person**: their best lift for that muscle, set against strength standards adjusted for bodyweight, age and sex. Tap a muscle (or its row in the list under the figures) for the best lift, the set it came from, and what the next level takes.

- **Level** = how many of five thresholds (Beginner, Novice, Intermediate, Advanced, Elite) the estimated 1RM reaches; below the first is *Untrained*; no counting lifts is *No data*. A muscle takes its best exercise (highest level, ties to the one further toward the next). The 1RM is the app's own estimate (Epley fed logged reps + RIR, sets over 12 effective reps ignored), same as the Records cards.
- **The standards are rounded rule-of-thumb multiples of bodyweight**, per lift family (`FAMILIES`), written for an 80 kg adult man in his prime. `EXERCISES` says which muscles each exercise counts toward and scales its family (`factor`: 0.4 = a dumbbell lift entered per dumbbell; `bw`: the fraction of bodyweight that's part of the load, which is why a bodyweight pull-up counts with nothing added). Unlisted exercises (assisted pull-ups, ab wheel, hip adduction, any custom exercise) don't colour the map. **A new stock exercise needs an `EXERCISES` entry** (with its `DEMOS`, `CURATED`, `ADJUST`…) or it silently won't count.
- **Adjusting for the person** (`thresholdsFor()`): bodyweight scales strength roughly ∝ bodyweight^(2/3) (`weightFactor()`, so a heavier lifter needs more kg but fewer per kilo); women's standards use ×0.62 upper / ×0.72 core / ×0.78 lower; `ageFactor()` eases the standards ~1%/year past 40 (faster later) and below 23, clamped to 14–90. These are approximations of the usual masters/juniors corrections, not a published table — say so, don't dress them up.
- **Inputs:** bodyweight is the latest weigh-in in Body (read straight from LifeDB), falling back to a typed weight if there are none; age and "compare me with" (men's/women's standards) are asked once and kept in Gym's settings as `strengthProfile` `{age, ageOn, sex, weightKg?}` — the age is stored with the day it was entered and rolled forward by `currentAge()`, so it keeps itself current. Nothing is assumed about sex: until it's chosen the card shows the setup form instead of the map.
- **Colour** is the six `--level-0…5` tokens in `life.css`: one terracotta hue, light to dark (dark mode flips so higher is brighter), *validated as an ordinal ramp on each surface* (monotone lightness, every step ≥0.06 apart, lightest ≥2:1) — re-validate if you touch them. `--level-none` is no data. Colour is never the only channel: legend, detail panel and a text list all say the level.
- **The drawing is original**: `body-shapes.js` is point lists in a 220×470 box that `smoothPath()` turns into closed Catmull-Rom curves (`side` shapes are mirrored across x=110, `centre` shapes drawn once), so a muscle is reshaped by moving points. Regions are `role="button"` groups; selection is repainted in place so a tap doesn't lose scroll or focus.
- `isLoggedWork()`/`estimateOneRepMax()` now live in `strength.js` (pure, Node-testable) and are shared by Records, Progress and the map.

### Reordering exercises in a workout (`initDragHandle()`, `moveExercise()` in `workout.js`)

Two ways, both ending in `render()` and then `showMovedBlock()`, which scrolls the moved block to the top of the screen and pulses it so you can see where it landed in a list that just changed height.

- **Drag the ☰ handle** (a 40×48 target). A press only becomes a drag after the finger travels `DRAG_START_PX` (8) — a tap, or a thumb that lands on it while scrolling, does nothing. Then the list collapses to just names, the page is scrolled so the block sits under the finger (the collapse otherwise leaves the scroll position wherever the browser clamped it, often with the top of the list out of reach), and it follows the finger. **Within ~80px of the top or ~130px of the bottom (above the nav) the page auto-scrolls**, faster nearer the edge (`autoScroll()`, once per frame), so the far end of a long workout is reachable without letting go.
- **Edit → ↑ Move up / ↓ Move down** (`.block-move`, shown only in edit mode): one place at a time, the block stays in edit mode so the next tap is right there; disabled at the ends.
- **The dragged block's transition is forced off with an inline `!important`.** `naturalTop()` sets `transform: none` and reads the position straight back, and the global reduced-motion rule leaves every element a 0.01ms transition — enough to return the stale position until the next frame, so with Reduce Motion on (or a hidden tab) the block drifted off the finger. Don't read a position back after setting a transform without making sure no transition is running.
- **Never move the dragged block in the DOM, and never listen for its release on the handle alone.** The first version swapped places with `insertBefore(block, …)`; on a phone that takes the node out of the document, the browser drops the finger's hold on it, the "finger lifted" event goes elsewhere, and the list stays collapsed with a block stuck to a finger that isn't there (it moved one place, then stopped following). Now `checkSwap()` moves the blocks the dragged one crossed (`block.after(...passed)` / `block.before(...passed)`, animated by `flipSiblings()`), and move/release are caught on the **window** for the one `pointerId` that started the drag, with backups so it can't strand (`touchend`/`touchcancel`, `blur`, `pagehide`, the tab hiding, a mouse move with no button down, a new press by another pointer). Everything funnels into one idempotent `finish()`.
- **To test it, simulate the loss, not just the happy path:** after the first swap, send the remaining pointer events to `document.body` instead of the handle, and watch a `MutationObserver` for the dragged block being removed. Events dispatched straight at the handle, which the earlier tests did, can never show this bug.
- Testing this in the preview pane: it reports Reduce Motion and `visibilityState: hidden`, so `requestAnimationFrame` never fires — swap it for a `setTimeout` in the test.

### Last time in this plan (`lastPlanPerformance()` in `store.js`, `setRow()`/`refreshPlanHints()` in `workout.js`)

In a workout started from a saved plan, each working set's reps box carries a small faded "last N": the reps from the same set number the last time that **slot** of **this plan** was done. It is scoped to the plan (`workout.templateId`) on purpose — the same lift is a heavy 4×6 in Push and a lighter 3×12 in Upper — so it differs from the older "Last time" line above the sets (`lastPerformance()`), which looks across every workout and also seeds the weights. It is a caption, not a value: `.reps-ghost` is not focusable, selectable or tappable, sits outside the input, and is never saved. Warm-ups neither show nor use it; a set beyond what you did last time has none; a quick workout (no plan) has none.

- **Matched by slot, not by exercise** (`slotOf()`: the exercise the plan asked for, i.e. `swappedFromId ?? exerciseId`). A session where the slot was done through **Swap** still counts as the last time that slot was done; matching on the exercise alone skipped it and fell back to a workout from weeks earlier, so the numbers looked like they hadn't updated.
- **It updates every time a workout is completed** because it is never cached: `finishWorkout()` reloads `state.workouts` before it redraws, and each block reads them when it is built (and again on every `refreshSets()`, so adding or removing a set can't use stale data). Only finished workouts count — a discarded or still-open session never does.
- **It also follows the saved workouts while a workout is open.** `loadWorkouts()` emits `workouts`, and `refreshPlanHints()` repaints the captions *in place* (shared `paintRepsGhost()`), so a workout edited or deleted in History, or a restored backup, changes the hints without rebuilding the blocks — a half-typed note, ticked sets, Edit mode and the scroll position are left alone. Don't "fix" staleness by calling `render()` here.
- **Testing:** drive a real finish (set reps, tick, Finish, confirm) and restart the plan without a reload; and discard sessions with the real Discard button — deleting the saved session behind the app's back leaves the in-memory `session` set, so `startWorkout()` silently refuses to start the next one and the test is reading the old screen.

### Exercise demo clips (`gym/js/demos.js`, `demo-link.js`)

Every stock exercise has a demo: `DEMOS` maps its id to `[YouTube video id, channel]`, with the clip's own title as a comment so a link can be checked against its exercise at a glance. The app **links out, it doesn't host or copy**: a "▶ Watch demo" link under the name in a live workout, and a thumbnail card in the exercise details, both opening the real video in a new tab (`demoLink()`; same approach as Videos — no embedded player, and it needs a connection). The still comes from `i.ytimg.com` and drops away quietly if it can't load. Videos belonging to someone else aren't bundled into the repo (it's public) — keep it that way; the exercise's own *clip/photo* in the Library is the offline, on-device option.

- **Every pick was checked against YouTube when added** (it resolves via oEmbed, and its title names this exercise and equipment), preferring short, established coaching channels. Custom exercises have no entry and show no link. Dead links can't be detected offline, so if one rots, swap its id here.
- **Adding a stock exercise to `seed.js` means adding a `DEMOS` entry too** (alongside its `CURATED` list and, if needed, a role and `ADJUST` entry).

### Shared UI primitives (`dom.js`, `stepper.js`, `sfx.js`)

`dom.js` provides `el()` (builds an element from a props+children object, always via `textContent`, never `innerHTML`), a **modal stack** (`openModal`/`closeModal`/`onModalClosed`), `toast()`, and `confirmSheet()` — a promise-based confirm dialog. Every modal in the app is static markup already present in `index.html`, shown/hidden via the stack rather than created dynamically. **The stack also makes every sheet accessible, in one place, so no sheet's markup needs editing:** `openModal()` marks the `.modal-content` as `role="dialog"` + `aria-modal` named by the sheet's `h2` (`confirm-modal` is an `alertdialog` described by its message), makes everything outside the top sheet `inert` + `aria-hidden` (the toast excepted, so it can still be heard; each element it marks carries `data-modal-inert`, and closing the last sheet — or calling `closeModal()` with none open — releases every one, so a missed close can't freeze the app), and focuses the sheet's panel, **never a field** (that would raise the iOS keyboard; the exercise picker deliberately has no autofocus). Closing returns focus to whatever opened it unless that was a text field or has since been re-rendered away; Tab wraps within the top sheet. A new sheet needs only an `h2` in its `.modal-header`. `#toast` is static markup with `role="status"` so its text is announced. `confirmSheet()` resolves exactly once no matter how the sheet closes (Confirm, Cancel, backdrop tap, or Escape) — always reuse it for destructive-action confirmation rather than wiring up ad-hoc confirm logic.

`stepper.js` is the shared −/+ numeric input used everywhere (reps, weight, sets, rest seconds): live keystroke filtering plus min/max clamping. Its buttons use `bindHold()` (`dom.js`): a press acts on `pointerdown` and repeats while held, and a plain `click` — Enter/Space, a switch or a screen reader — steps once, ignored when it is just the tail of a pointer press (while held, or within 600 ms of release). `sfx.js` owns one shared `AudioContext` (unlocked on first tap, since iOS blocks audio before a user gesture) for all sound effects — reuse it rather than creating a second context.

### Units convention

Weight is **always stored in kg** in the database. Conversion to/from the user's chosen display unit (`units.js`: `toDisplay`/`fromDisplay`, `kg`↔`lb`) happens only at the display/input boundary. Never persist a `lb` value.

### PWA / offline layer

`sw.js` is the single root service worker for all of Life (cache name `life-<version>`), versioned and cache-first. `CACHE_VERSION` **must be bumped whenever any file in `APP_SHELL` changes** (including adding a new `gym/js/*.js` or `life/*` file to that list) — otherwise the service worker keeps serving the previous cached version indefinitely, both to yourself in local testing and to real installs after a deploy. **A version installs whole or not at all.** Install fetches every `APP_SHELL` file (straight from the network, `cache: 'no-store'`, never the browser's HTTP cache, which GitHub Pages lets hold a file for 10 minutes), six at a time, retrying a dropped connection or a 5xx up to three times (a 404 is not retried — it won't appear). If any file still can't be had, the install **fails**: the half-built cache is deleted, nothing activates, the previous version keeps running untouched, and the browser tries again on the next load or foreground check. This replaced "shrug off individual misses and activate anyway", which let an incomplete update replace a complete version and leave the app unable to start offline when a file never arrived. After a *complete* install the worker `skipWaiting()`s and `clients.claim()`s, so the next fetch is the new version.

**Updates reach an open app** (`life/updates.js`). A home-screen app on iOS is usually suspended, not closed, so a browser — which only looks for a new version when a page loads — could leave a deploy unseen for days. The page therefore calls `registration.update()` when it returns to the foreground (at most every 15 minutes) and hourly while open. Once a new worker takes over, a page that **was already controlled when it loaded** shows an "A new version is ready" banner with **Reload** / **Later**, because the code on screen is still the old version; it never reloads by itself (a reload mid-set would be rude — the open workout is saved with every edit, so nothing is lost by waiting). The very first install also changes the controller and deliberately shows nothing. Test a worker change for real by editing `CACHE_VERSION` between `registration.update()` calls; to test the refusal, move one shell file out of the way and bump the version.

`manifest.webmanifest` and the icons in `icons/` support "Add to Home Screen" on iOS. Media (exercise demo photos/clips) is excluded from the JSON export/import backup in `settings.js` — blobs can run into the hundreds of megabytes.
